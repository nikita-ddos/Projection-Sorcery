1. WHAT THIS IS
------------------------------------------------------------------------------
A Minecraft mod (NeoForge 1.21.1, Java 21) that recreates Naoya/Naobito Zenin's
"Projection Sorcery" from Jujutsu Kaisen, modeled on the Fabric mod "Arlo's /
Orlan's Projection Sorcery" (1.21.1, All Rights Reserved -> NEVER copy its code;
only the general idea was used: phases IDLE/PLANNING/REPLAY, recorded frames,
attack frames).

Core idea: the player plans a path in "frozen time" (client-side simulated body),
then the server replays it frame by frame with teleports, attacks and insta-mined
blocks. Extras: cursed energy (CE), freeze-in-glass penalty, targets, "touch"
(impose the 24-frame rule on a victim), afterimages, themes.

Mod id: projectionsorcery      Package: com.projectionsorcery
Version history:
  1.0.0 RELEASE  first version (free camera, server blink, no CE system)
  1.0.1 BETA     physics body, CE, freeze, multiplayer limits, targets, touch,
                 afterimages, settings GUI
  1.0.2 BETA     server path validation, tick-rate-1 instead of /tick freeze,
                 opOnly removed, red victim blocks, Naoya/Naobito visuals
Keep CHANGELOG_AND_GUIDE.md updated for every new version (user asked for it;
label versions like "1.0.3 / BETA").

4. RUNTIME FLOW
------------------------------------------------------------------------------
PLANNING SESSION
 1. Client R (IDLE) -> StartRequest. Mode REQUESTING (60 tick timeout).
 2. Server (ServerTickEvent.Post): requests collected per tick.
      >1 request in the same tick -> ALL denied ("Simultaneous use").
      otherwise first come first served; denied if someone else has a session,
      player is replaying/frozen, or on cooldown.
    Grant: sessionOwner set; server tick rate lowered to 1 via
    server.tickRateManager().setTickRate(1.0F) (remembers previous rate; NO
    command is used, so no chat feedback); Session(1,maxTicks) sent.
    maxTicks = 0 (unlimited) unless players online > playerThreshold(2): then
    maxPlanSeconds*20 (3 s) and after the session a 5 s cooldown (wall clock).
 3. Client PLANNING: creates PlanBody (Sim.hero) as camera entity
    (mc.setCameraEntity). Real LocalPlayer input is zeroed via
    MovementInputUpdateEvent. Every client tick: Sim.tick(), record Frame if the
    body moved / rotated / action pending. Client resets its own tick rate to 20
    every frame (RenderFrameEvent.Pre) because the server tick-rate packet would
    otherwise slow the planner's client too.
    Air jump -> Jump payload -> server adds exhaustion (jumpHungerCost*4).
    LMB: entity in reach 3 -> STRIKE frame; block in reach 4.5 -> BREAK frame
    (block removed LOCALLY only so you can plan through it; restored before
    sending); nothing -> STRIKE. Blocks with hardness<0 or blast resistance >
    maxBlastResistance(32) are refused.
    RMB on a highlighted target route -> executes that route.
 4. Execute (R / route / time limit): client restores local blocks, sends
    TouchPlan (optional) then PlanChunk(s). Server onPlan(execute=true): creates
    Replay (with a PathValidator) and IMMEDIATELY ends the session -> tick rate
    restored (requirement: restore on execute, not when the replay finishes).
 5. Replay (ServerTickEvent.Post, replayFramesPerTick frames per tick, default 4):
    per frame: validate path -> spend CE (frame cost) -> sp.connection.teleport
    -> STRIKE: spend attackCost + damage entities on a ray (config reach 3.5) ->
    BREAK: validate block, spend blockCost, drop loot with the held tool
    (Block.dropResources) but NO durability damage, destroyBlock(drop=false).
    -> touch arming when the victim is within touch range.
    Result codes: 0 ok, 1 out of CE (-> finish + FREEZE), 2 invalid path (-> stop).
    finish(): zero velocity, lift the player upward if inside blocks.
 6. Player is invulnerable (LivingIncomingDamageEvent) while owning a session or
    replaying (except damage that bypasses invulnerability).

QUICK MOVE (V): client raycasts, finds a collision-free spot, builds a straight
path via PathPlanner.fromPoints(step 0.28) and sends it with sendPlan() - same
pipeline as every other path (user requirement). No session / no tick rate change.
QUICK MOVE TO TARGET (B): computeCandidates() -> shortest -> sendPlan().

TARGET (Z): CLIENT ONLY (nobody else is told). Entity id or BlockPos stored in
ClientEvents; red box rendered. In planning, up to 4 routes (direct + 4 detours,
deduplicated) to the target's BACK (PathPlanner.goalBehind) or to the block
(goalForBlock) are drawn; the one under the crosshair is highlighted.

TOUCH (C) - planning only: nearest Player/Mob within touch range of the planning
body. Mode TOUCH: camera moves to a victim body (Sim.victim, vanilla-like physics,
no air jumps), max 10 blocks traveled. Waypoints = grounded block positions.
Press C again -> back to own plan. On execute the TouchPlan is sent; server arms
the touch when the player comes within 3 blocks of the victim during the replay:
  player victim: gets TouchFx (red markers), 2 s aware time, then 1 s per block,
  timer resets each block, timer 0 -> FREEZE. Mobs are teleported along the path.

FREEZE (glass): player cannot move/turn for 1 s, glass placed in feet+head blocks
(only replaces air/replaceable), glass-break sound on place and on removal.
Server pulls the player back if they move; client zeroes input and locks the
camera angles (ViewportEvent.ComputeCameraAngles).

CE: Config cursedEnergy.infinite (default true). If false: max, regenPerTick,
frameCost 15, attackCost 45, blockCost 150. Stored in player persistent data
(key "projectionsorcery_ce"), synced to client every 10 ticks if changed.

5. PATH VALIDATION (PathValidator) - requirement text
------------------------------------------------------------------------------
"The path can go max 3 blocks off the physically possible course, or 5 if the
player was jumping."
Implementation: for each frame, a sim body (0.6x1.8 AABB, starts at the player's
real position) moves toward the claimed FEET position (frame y - 1.62), limited
to sprint speed*1.15 per frame, with gravity, jumps (infinite air jumps), step
height 3, water walking, collision from the LIVE world (so blocks broken earlier
in the replay are gone). Accepted if |claimed - sim| <= 3 (<= 5 if sim airborne or
claimed above sim by >0.05). The sim does NOT resync to the claimed position.
Caveats: no ladders/vines/scaffolding/bubble columns/honey etc.; frames are
assumed 1 per client tick; tolerances are config values.

6. USER REQUIREMENTS (full list, for reference; all implemented unless noted)
------------------------------------------------------------------------------
- NeoForge 1.21.1, like Arlo's mod; unlimited frames and CE (CE configurable).
- Planning: temp body with the player's stats, obeys Minecraft physics; infinite
  air jumps costing 0.5 hunger each (configurable); step up to 3 blocks (slabs,
  stairs, full blocks); walks on water; not slowed by powder snow/water; rest of
  the world slowed (now: server tick rate 1); insta-mine marking without tool
  durability use.
- Anime accuracy: cannot break unbreakable blocks or blast resistance > 32.
- CE: configurable; if finite: 15/frame, 45/attack frame, 150/broken block; out
  of CE while replaying -> freeze.
- "Freeze them" = stop camera+body 1 s, 2 glass blocks, glass-break sound on
  place and on removal.
- Two players starting in the same tick: both cancelled; otherwise the first wins.
- >2 players online: 5 s cooldown, planning max 3 s.
- Target keybind (client only, red indicator); target routes to the target's back;
  aim + right click executes; Quick move to target = same routes, shortest one,
  instantly. Block targets: same with a path to the block.
- Touch keybind (see section 4).
- Afterimages of own planned moves and the victim's planned moves, translucent,
  colored by theme, with a highlight.
- Settings GUI: theme Naoya/Naobito (user plans to add more later).
- Quick move (V): same function as executing a predetermined path, skipping
  planning.
- Server-side path validation (3 / 5 blocks).
- Tick rate 1 for everyone except the planner (not freeze); NOT opOnly; no one but
  the planner should see changes before execution; tick rate back to 20 when
  EXECUTED (not when the replay ends).
- Victim blocks highlighted RED regardless of theme.
- Naoya theme: in-world projection translucent blue/cyan (transparency 0.3-0.4);
  planner's whole screen overlaid with slightly transparent blue (0.5-0.6).
- Naobito theme: in-world projection fully transparent with solid white outlines;
  planner's screen gets a small black tint (0.8-0.9).
  >>> I interpreted "transparency" as the fraction that is transparent (so
  >>> ghost alpha ~0.65, Naoya overlay alpha ~0.45, Naobito tint alpha ~0.15).
  >>> The user has not confirmed this. Easy to flip in Theme.java.
  >>> Colors were NOT verified against reference images (image search is not
  >>> allowed for anime content; text search gave nothing).

7. KNOWN INTERPRETATIONS / OPEN QUESTIONS (ask the user if unsure)
------------------------------------------------------------------------------
- "no one except the user should see anything changing before the plan gets
  executed": implemented as: nothing is broadcast (no command feedback), blocks
  are only changed locally, afterimages/overlay/targets are client-only. BUT the
  tick rate is server-global and vanilla sends a ClientboundTickingStatePacket
  to every client, so OTHER players' worlds visibly slow to 1 tick/s while
  someone plans. This is an unresolved conflict with the user's wording. Options:
  (a) accept; (b) a mixin to suppress the packet for non-planners (mod currently
  uses no mixins) - still leaves server-driven entity updates at 1/s for them;
  (c) per-player slow motion done purely client-side while the server stays at
  20 TPS (breaks "world is really frozen while planning"). Ask the user.
- 0.5 hunger per air jump = 2.0 exhaustion (4 exhaustion = 1 hunger point).
  Not refunded on cancel.
- Touch triggers the first time the player is within range of the victim during
  the replay; victim waypoints = blocks the victim sim stood on.
- Cooldown starts when ANY session ends (execute/cancel/timeout).
- Quick move is validated and therefore walking pace (0.28/frame); the user has
  not commented on the lost "insta" feel. Replay speed is the lever
  (replayFramesPerTick).

9. KNOWN BUGS / LIMITATIONS / IDEAS
------------------------------------------------------------------------------
- PathPlanner: slabs/stairs count as non-standable ground; 6000 node cap; may
  find no route in complex terrain; linear height interpolation for steps.
- Step height 3 may look odd under ceilings (vanilla step algorithm).
- Water walking can jitter on flowing water; no lava/damage-block avoidance in sim.
- Replay that ends inside blocks lifts the player to the first free spot upward
  (can be far in caves).
- Insta-mine ignores claim/protection mods (only vanilla restrictions checked).
- Afterimages: flat-color silhouettes for every entity (no skin/armor).
  Naobito outline shows every quad edge (also hidden faces).
- Camera lock during freeze is client-side + server pull-back; a modified client
  can ignore the lock (server still pulls position back).
- Only one touch target per plan. Touch victim that is the planner's own
  target is not specially handled.
- No sounds/particles for planning start/end (could add, but "nobody else should
  notice" - keep client-only).
- Ideas the user mentioned wanting later: more themes (add to Theme enum), more
  GUI settings.
- Possible cleanups: unit-testable PathValidator, config for ghost count/distance,
  localisation of HUD strings (currently hard-coded English), server messages.
